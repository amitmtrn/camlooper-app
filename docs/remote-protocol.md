# Phone camera stream — signaling protocol (remote v2)

The phone (a web page in Android Chrome) streams its camera to the desktop app over a
peer-to-peer WebRTC connection. The relay at `api.camlooper.com` only forwards signaling and
hands out STUN servers; media never touches it.

This document defines the **app-level** messages that travel inside the relay's frames. The
relay transport itself (`hello`, `peer`, `signal`, `stream_stop`, `error`, tickets, limits) is
specified in the server repo's README, section "Protocol v2". The desktop implementation is
`src-tauri/src/remote/stream/signal.rs` (types and validation) and `machine.rs` (rules).

## Transport recap

- Desktop: `GET wss://api.camlooper.com/v1/desktop/ws?protocol=2` with
  `Authorization: Bearer <desktopToken>` and `X-CamLooper-Pair: <pairId>` (native client, no
  `Origin`). v1 frames (`open_meeting`, `ack`, `ping`/`pong`, `unpaired`) are unchanged on this
  socket.
- Phone: `wss://api.camlooper.com/v1/mobile/ws?pair=<pairId>&ticket=<ticket>`.
- Either side sends `{"type":"signal","data":{…}}`; the other receives
  `{"type":"signal","from":"mobile"|"desktop","data":{…}}`. `data` is one message below.
- Either side ends a stream with `{"type":"stream_stop","data":{"sessionId":…,"reason":…}}`.
- Presence: the desktop gets `hello{protocol:2, mobileDeviceName, peerOnline}` on connect and
  `peer{role:"mobile", online}` on changes.
- Limits: 16 KB of UTF-8 per frame, 300 relayed frames per minute per socket.

## Messages (`signal.data`)

All messages carry `kind` and `sessionId`. `sessionId` is generated by the phone for each
attempt: 1–64 printable ASCII characters, no spaces (e.g. 16 random base64url characters).

| `kind` | Direction | Fields | Meaning |
|---|---|---|---|
| `stream_request` | phone → desktop | `sessionId`, `deviceLabel?` (≤ 64 chars) | "May I stream my camera?" The desktop asks its user. |
| `stream_accept` | desktop → phone | `sessionId` | The user accepted. Send the offer now. |
| `stream_reject` | desktop → phone | `sessionId`, `reason`: `declined` \| `busy` \| `timeout` \| `unsupported` | No stream. `busy`: another session is active. `timeout`: nobody answered within 60 s. |
| `offer` | phone → desktop | `sessionId`, `sdp` (≤ 14 KB) | The phone's SDP offer (video sendonly; an audio m-line is accepted and ignored). |
| `answer` | desktop → phone | `sessionId`, `sdp` | The desktop's answer. **All desktop candidates are embedded in it**; the desktop does not trickle. |
| `candidate` | phone → desktop (either direction allowed) | `sessionId`, `candidate`, `sdpMid?`, `sdpMLineIndex?` | One trickled ICE candidate (`candidate:…`, an `a=` prefix is tolerated). Empty string or `null` = end of candidates. |
| `status` | desktop → phone | `sessionId`, `state`: `connecting` \| `live`, `width?`, `height?`, `fps?`, `codec?` (`H264` \| `VP8`) | Progress for the phone's UI. `live` is sent when the first frame reaches the virtual camera, and again (at most every 2 s) when codec or resolution changes. |

Stop (`stream_stop.data`): `{sessionId, reason}` with `reason` one of `user`, `ice_failed`,
`error`, `peer_offline`, `timeout`. Unknown reasons are accepted. A `stream_stop` without
`data` or without `sessionId` stops the current session (there is only ever one).

Unknown `kind`s, malformed messages and messages whose `sessionId` is not the current
session's are ignored (logged without content).

## Sequence

```text
phone                                   relay                         desktop
  │ signal{stream_request, s1, "Pixel"}   │                               │
  │──────────────────────────────────────▶│──────────────────────────────▶│ ask the user (≤ 60 s)
  │                                       │   signal{stream_accept, s1}   │
  │◀──────────────────────────────────────│◀──────────────────────────────│
  │                                       │ signal{status, connecting}    │
  │◀──────────────────────────────────────│◀──────────────────────────────│ hand the camera over,
  │ signal{offer, s1, sdp}                │                               │ bind sockets, STUN
  │──────────────────────────────────────▶│──────────────────────────────▶│
  │ signal{candidate, s1, …} (trickle)    │   signal{answer, s1, sdp+cands}│
  │──────────────────────────────────────▶│◀──────────────────────────────│
  │◀═════════════════ ICE / DTLS / SRTP, peer to peer ═══════════════════▶│
  │                                       │ signal{status, live, 1280×720}│
  │◀──────────────────────────────────────│◀──────────────────────────────│
  │ stream_stop{s1, user}   (or the desktop sends it)                     │
  │──────────────────────────────────────▶│──────────────────────────────▶│ restore the video loop
```

The phone may send its offer before `stream_accept`; the desktop holds it (and up to 64 early
candidates) until the user accepts. Waiting for `stream_accept` is still recommended, so a
declined request costs the phone no camera start.

## Rules and timeouts (desktop)

| What | Value | Result |
|---|---|---|
| Sessions | one at a time | a `stream_request` with another `sessionId` while busy → `stream_reject{busy}` |
| User decision | 60 s | `stream_reject{timeout}` |
| Accepted, no offer | 20 s | `stream_stop{timeout}` |
| Offer → ICE connected | 15 s | `stream_stop{ice_failed}` |
| No video while connected | 10 s | `stream_stop{timeout}` |
| Phone leaves the relay | `peer{online:false}`, `hello{peerOnline:false}` or `error{peer_offline}` | the stream stops (`peer_offline`, nothing is sent) |
| Phone sends `stream_stop` | — | the stream stops; nothing is sent back |
| Desktop failure (ffmpeg restarted 3×, camera unavailable) | — | `stream_stop{error}` |

## Media

- **Codecs:** H.264 (packetization-mode 1; constrained baseline, baseline, main, high) is
  preferred, VP8 is the fallback. The desktop answers with the first of its codecs that the
  offer contains, so the phone's codec order does not matter.
- **ICE:** STUN only (`/v1/ice-servers`), no TURN, so the phone and the computer are expected to
  be on the same network (or have a working NAT path). The desktop offers one host candidate per
  usable IPv4 interface plus at most one server-reflexive candidate. It cannot resolve mDNS
  (`*.local`) candidates; Chrome exposes real host addresses to a page that holds camera
  permission, and the phone also reaches the desktop's host candidates directly
  (peer-reflexive), so this does not block same-LAN connections.
- **Bandwidth:** the answer keeps `transport-cc` and the transport-wide sequence-number header
  extension (the desktop sends TWCC feedback) and `goog-remb` (the desktop sends REMB with an
  8 Mbit/s ceiling), so Chrome's estimator can ramp up from its initial low resolution.
- **Keyframes:** the desktop sends PLI when the track starts, after loss, when its decoder
  (re)starts, and when no frame arrived for 1 s — at most one per second.

### Recommendations for the phone page

- Capture with `getUserMedia({video: {width: {ideal: 1280}, height: {ideal: 720}, frameRate: {ideal: 30}}})`.
- Chrome starts at a low resolution and ramps up with its bandwidth estimate. To reach 720p
  sooner: `sender.setParameters()` with `encodings[0].maxBitrate ≈ 2_500_000` and
  `degradationPreference: "maintain-resolution"` (or `"balanced"`), and
  `track.contentHint = "motion"`.
- Portrait video is fine: the desktop letterboxes it into the camera's 16:9 frame.
- Send `stream_stop{reason:"user"}` when the user stops, and before the page is hidden or
  closed (`pagehide`).
