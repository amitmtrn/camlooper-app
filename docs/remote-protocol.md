# Phone camera stream — signaling protocol (remote v2)

The phone (a web page in Android Chrome) streams its camera to the desktop app over a
peer-to-peer WebRTC connection. The relay at `api.camlooper.com` only forwards signaling and
hands out STUN servers; media never touches it.

This document defines the **app-level** messages that travel inside the relay's frames. The
relay transport itself (`hello`, `peer`, `signal`, `stream_stop`, `error`, tickets, limits) is
specified in the server repo's README, section "Protocol v2". The desktop implementation is
`src-tauri/src/remote/stream/signal.rs` (types and validation) and `machine.rs` (rules).

## Transport recap

- Desktop: `GET wss://api.camlooper.com/v1/desktop/ws?protocol=2` with
  `Authorization: Bearer <desktopToken>` and `X-CamLooper-Pair: <pairId>` (native client, no
  `Origin`). v1 frames (`open_meeting`, `ack`, `ping`/`pong`, `unpaired`) are unchanged on this
  socket.
- Phone: `wss://api.camlooper.com/v1/mobile/ws?pair=<pairId>&ticket=<ticket>`.
- Either side sends `{"type":"signal","data":{…}}`; the other receives
  `{"type":"signal","from":"mobile"|"desktop","data":{…}}`. `data` is one message below.
- Either side ends a stream with `{"type":"stream_stop","data":{"sessionId":…,"reason":…}}`.
- Presence: the desktop gets `hello{protocol:2, mobileDeviceName, peerOnline}` on connect and
  `peer{role:"mobile", online}` on changes.
- Limits: 16 KB of UTF-8 per frame, 300 relayed frames per minute per socket.

## Messages (`signal.data`)

All messages carry `kind` and `sessionId`. `sessionId` is generated by the phone for each
attempt: 1–64 printable ASCII characters, no spaces (e.g. 16 random base64url characters).

| `kind` | Direction | Fields | Meaning |
|---|---|---|---|
| `hello` | phone → desktop | `sessionId` (any valid id; no session is needed), `appProtocol` (integer ≥ 1; `3` today) | "Which app protocol do you speak?" Sent once after pairing, when the desktop is online. See [App protocol 3](#app-protocol-3-hello-and-record-mode). |
| `hello_ok` | desktop → phone | `sessionId` (the same), `appProtocol`: `3`, `features`: e.g. `["live","record","file"]` | The answer. `features` are the `stream_request` modes this desktop takes. |
| `stream_request` | phone → desktop | `sessionId`, `deviceLabel?` (the desktop strips control and invisible/bidi format characters and keeps the first 40 characters), `mode?`: `live` (default) \| `record` \| `file` (with `file: {name, size, mime}`) | "May I stream my camera?" — with `record`: "…and loop what I film?" The desktop asks its user. |
| `stream_accept` | desktop → phone | `sessionId` | The user accepted. Send the offer now. |
| `stream_reject` | desktop → phone | `sessionId`, `reason`: `declined` \| `busy` \| `timeout` \| `unsupported` | No stream. `busy`: another session is active. `timeout`: nobody answered within 60 s. |
| `offer` | phone → desktop | `sessionId`, `sdp` (≤ 14 KB) | The phone's SDP offer (video sendonly; an audio m-line is accepted and ignored). |
| `answer` | desktop → phone | `sessionId`, `sdp` | The desktop's answer. **All desktop candidates are embedded in it**; the desktop does not trickle. |
| `candidate` | phone → desktop (either direction allowed) | `sessionId`, `candidate`, `sdpMid?`, `sdpMLineIndex?` | One trickled ICE candidate (`candidate:…`, an `a=` prefix is tolerated). Empty string or `null` = end of candidates. |
| `status` | desktop → phone | `sessionId`, `state`: `connecting` \| `live`, `width?`, `height?`, `fps?`, `codec?` (`H264` \| `VP8`); record sessions: `mode`: `record`, and once the take has started `record: {elapsedMs, capMs, phase, error?}` | Progress for the phone's UI. `live` is sent when the first frame reaches the virtual camera, and again (at most every 2 s) when codec or resolution changes. In a record session also when the take starts and when it is being processed. |
| `loop_control` | phone → desktop | `sessionId` (any valid id), `action`: `stop` \| `start` \| `status` | Act on the video that loops on the desktop. No session needs to be open; refused (`busy`) while one is. `start` never turns on a virtual camera that is off (`camera_off`). |
| `loop_status` | desktop → phone | `sessionId`, `playing`, `name?`, `fromPhone`, `error?` | The answer to `loop_control`, and sent after every file or record session. |

Stop (`stream_stop.data`): `{sessionId, reason}` with `reason` one of `user`, `ice_failed`,
`error`, `peer_offline`, `timeout`, and from the desktop at the end of a file or record
session `done` (a success: the video loops), `too_short` and `incomplete` (record only, see
below). Unknown reasons are accepted. **`sessionId` is required
once the desktop has accepted the session:** a `stream_stop` without `data` or without
`sessionId`, or naming another session, is ignored then (a late stop from an earlier attempt
must not end the stream that is running). Before the user has decided, a `stream_stop`
without `sessionId` still cancels the pending request.

`peer_stopped` is a desktop-local reason (logs, `phone_stream_cli` output) for "the phone
closed the peer connection and no `stream_stop` followed". It is never sent on the wire.

Unknown `kind`s, malformed messages and messages whose `sessionId` is not the current
session's are ignored (logged without content).

## Sequence

```text
phone                                   relay                         desktop
  │ signal{stream_request, s1, "Pixel"}   │                               │
  │──────────────────────────────────────▶│──────────────────────────────▶│ ask the user (≤ 60 s)
  │                                       │   signal{stream_accept, s1}   │
  │◀──────────────────────────────────────│◀──────────────────────────────│
  │                                       │ signal{status, connecting}    │
  │◀──────────────────────────────────────│◀──────────────────────────────│ hand the camera over,
  │ signal{offer, s1, sdp}                │                               │ bind sockets, STUN
  │──────────────────────────────────────▶│──────────────────────────────▶│
  │ signal{candidate, s1, …} (trickle)    │   signal{answer, s1, sdp+cands}│
  │──────────────────────────────────────▶│◀──────────────────────────────│
  │◀═════════════════ ICE / DTLS / SRTP, peer to peer ═══════════════════▶│
  │                                       │ signal{status, live, 1280×720}│
  │◀──────────────────────────────────────│◀──────────────────────────────│
  │ stream_stop{s1, user}   (or the desktop sends it)                     │
  │──────────────────────────────────────▶│──────────────────────────────▶│ restore the video loop
```

The phone may send its offer before `stream_accept`; the desktop holds it (and its early
candidates) until the user accepts. Waiting for `stream_accept` is still recommended, so a
declined request costs the phone no camera start.

## Rules and timeouts (desktop)

| What | Value | Result |
|---|---|---|
| Sessions | one at a time | a `stream_request` with another `sessionId` while busy → `stream_reject{busy}` |
| User decision | 60 s | `stream_reject{timeout}` |
| After the user declines | 15 s | new `stream_request`s → `stream_reject{declined}` without asking the user. Only an explicit decline starts this: not a timeout, a cancel by the phone, or an unlink |
| Confirm dialogs | 5 per 60 s | further `stream_request`s → `stream_reject{declined}` without asking the user, however the earlier ones ended |
| Accepted, no offer | 20 s | `stream_stop{timeout}` |
| Accepted, camera not ready (a polkit/UAC prompt may be open) | 120 s | `stream_stop{timeout}`, sent at the deadline even if the prompt is still open; the answer is sent only once the camera is ready |
| A stopped or failed session has not handed the camera back yet | until it has | `stream_request` → `stream_reject{busy}` (also after the desktop gave up waiting: 10 s, 125 s if the camera was still being prepared, or a forced stop by the user) |
| Remote candidates | 32 per session, counting those in the offer | the rest are ignored; so are non-UDP, non-IPv4, port 0, loopback, multicast and unspecified addresses |
| Offer → ICE connected | 15 s | `stream_stop{ice_failed}` |
| No video while connected | 10 s | `stream_stop{timeout}` |
| Phone leaves the relay before the stream is live | `peer{online:false}`, `hello{peerOnline:false}` or `error{peer_offline}` | the attempt ends (`peer_offline`, nothing is sent) |
| Phone leaves the relay while live | same | nothing at first: media is peer to peer. If the phone is still offline 10 s later **and** no frame arrived in that time, the stream stops (`peer_offline`, nothing is sent); while video keeps arriving it stays up. A media timeout while the phone is offline (per `peer`/`hello`) also ends as `peer_offline`, not as an error. An `error{peer_offline}` alone is only a hint: it is forgotten once video is seen to keep arriving |
| Phone sends `stream_stop` (with the session's id) | — | the stream stops; nothing is sent back |
| Phone closes the peer connection (DTLS close) | — | a normal stop, not an error. The desktop waits up to 1.5 s for the `stream_stop` that usually follows and uses its reason; nothing is sent back |
| Desktop relay socket reconnects | — | queued frames younger than 30 s are sent if they are about the current session or end one (`stream_stop`, `stream_reject`); the rest are dropped. A frame whose send failed with the old socket is sent first |
| Desktop is linked to another phone | — | nothing queued for the previous pairing is sent: a frame goes out only if its `sessionId` was received from the phone of the current pairing |
| Desktop failure (ffmpeg restarted 3× within 30 s, camera unavailable) | — | `stream_stop{error}` |

## Media

- **Codecs:** H.264 (packetization-mode 1; constrained baseline, baseline, main, high) is
  preferred, VP8 is the fallback. The desktop answers with the first of its codecs that the
  offer contains, so the phone's codec order does not matter.
- **ICE:** STUN only (`/v1/ice-servers`), no TURN, so the phone and the computer are expected to
  be on the same network (or have a working NAT path). The desktop offers one host candidate per
  usable IPv4 interface (at most 4, the default-route interface first; VPN/tunnel and
  container/VM bridge interfaces are left out) plus at most one server-reflexive candidate. It cannot resolve mDNS
  (`*.local`) candidates; Chrome exposes real host addresses to a page that holds camera
  permission, and the phone also reaches the desktop's host candidates directly
  (peer-reflexive), so this does not block same-LAN connections.
- **Bandwidth:** the answer keeps `transport-cc` and the transport-wide sequence-number header
  extension (the desktop sends TWCC feedback) and `goog-remb` (the desktop sends REMB with an
  8 Mbit/s ceiling), so Chrome's estimator can ramp up from its initial low resolution.
- **Keyframes:** the desktop sends PLI when the track starts, after loss, when its decoder
  (re)starts, and when no frame arrived for 1 s — at most one per second.

### Recommendations for the phone page

- Capture with `getUserMedia({video: {width: {ideal: 1280}, height: {ideal: 720}, frameRate: {ideal: 30}}})`.
- Chrome starts at a low resolution and ramps up with its bandwidth estimate. To reach 720p
  sooner: `sender.setParameters()` with `encodings[0].maxBitrate ≈ 2_500_000` and
  `degradationPreference: "maintain-resolution"` (or `"balanced"`), and
  `track.contentHint = "motion"`.
- `mode: "record"`: lock the picture instead. Capture the 720 preset (1280x720 @ 30) whatever
  the user's live quality is, and on the sender set `encodings[0].scaleResolutionDownBy = 1`,
  the preset's `maxBitrate`, and `degradationPreference: "maintain-resolution"`
  (`track.contentHint = "detail"` where that cannot be set), so that a bad network costs
  frames and not size. No camera switch during a take.
- Portrait video is fine: the desktop letterboxes it into the camera's 16:9 frame.
- Send `stream_stop{sessionId, reason:"user"}` when the user stops, and before the page is
  hidden or closed (`pagehide`). Always include `sessionId`. Closing the `RTCPeerConnection`
  alone also ends the session cleanly on the desktop, but without a reason.

## App protocol 3: `hello` and record mode

The app-level protocol has a version of its own, **3**, independent of the relay's
`?protocol=2` (which is unchanged). It exists so that a new phone page and an old desktop —
or the reverse — find out at once, instead of one side taking a request for something else
and the attempt ending as a timeout.

### `hello` / `hello_ok`

- After the phone is paired and the desktop is online, the phone sends once
  `{"kind":"hello","sessionId":"<valid id>","appProtocol":3}`.
- A desktop that speaks protocol 3 answers
  `{"kind":"hello_ok","sessionId":"<same>","appProtocol":3,"features":["live","record","file"]}`.
  `features` are the modes it takes. `record` and `file` are listed only when the desktop
  has a place to store a video (its app data directory); otherwise the list is `["live"]`.
- No `hello_ok` within 5 s, `appProtocol < 3`, or no `record` in `features`: the phone shows
  "Update CamLooper on your computer to record a loop." and does not enable Record. (An older
  desktop ignores the unknown kind, so the phone sees the timeout.)
- The desktop answers at most 5 `hello`s per 10 s; a `hello` without a numeric
  `appProtocol ≥ 1` is dropped as malformed. A phone's higher `appProtocol` is still
  answered with `3` — the phone decides what it can do with that.
- `hello` is **not** a precondition. A desktop takes a `mode: "live"` request (or one
  without `mode`, from an older phone page) and a `mode: "record"` request without a
  `hello` before it: the request itself is unambiguous.
- A `mode` the desktop does not know is answered `stream_reject{unsupported}`. It is never
  taken for `live`. The same answer is given to `record` / `file` on a desktop that has no
  place to store a video.

### `mode: "record"` — film on the phone, loop on the desktop

No file is transferred. The phone streams its camera exactly as for `live` — same
`RTCPeerConnection`, same ICE, same codecs, no data channel — and the desktop *tees* the
stream into a file while it shows it live on the virtual camera. When the take ends, the
desktop loops the file with the engine that loops a local video (natural motion included),
and the phone is no longer needed.

```text
phone                                                             desktop
  │ signal{stream_request, s1, mode:"record"}                        │ "Record a loop from <device>?"
  │ … stream_accept, status{connecting, mode:"record"}, offer, answer, ICE — as for live …
  │◀──── signal{status, live, mode:"record"} ────────────────────────│ first frame on the camera; pre-roll
  │◀──── signal{status, live, mode:"record",                         │ the take starts
  │        record:{elapsedMs:0, capMs:60000, phase:"recording"}} ────│
  │ stream_stop{s1, user}  (or 60 s pass, or the desktop's Stop)     │
  │◀──── signal{status, …, record:{…, phase:"processing"}} ──────────│ remux, load
  │◀──── stream_stop{s1, done} ──────────────────────────────────────│ looping
  │◀──── signal{loop_status, s1, playing:true, fromPhone:true} ──────│
```

| What | Rule |
|---|---|
| Confirm dialog | the same Accept / Decline / 60 s / busy / cooldown rules as `live`; the request the UI gets carries `mode: "record"` |
| Pre-roll | a WebRTC sender starts small and steps the picture up, and a take is one size. The take starts once the incoming picture size has been unchanged for 1 s, or 3 s after the stream went live, whichever is first: the desktop asks for a keyframe then and starts on it (after 500 ms without one, from the last keyframe of that size). Nothing of an earlier, smaller size is kept. The first `status` that carries `record` marks the start: `elapsedMs` counts from there |
| Size change during the take | larger, less than 3 s into the take: the take starts over at the larger size (the smaller prelude is deleted, `elapsedMs` goes back to 0, the 60 s cap counts from there). Otherwise the take keeps its size and frames of another size are left out until the stream is back at it |
| Cap | 60 s of take (`capMs`). The desktop finalizes then, whether or not the phone has stopped |
| Minimum | `MIN_TAKE_MS` = 2000 ms of teed media |
| The phone's `stream_stop`, the desktop's Stop / Cancel, or the phone closing the connection, **during the take** | ≥ 2 s teed: the take is finalized and looped; the session ends with `stream_stop{done}` from the desktop (also when it was the phone that stopped) followed by `loop_status`. < 2 s: the partial file is deleted and nothing loops; after the phone's stop the desktop answers `stream_stop{too_short}`, after its own it sends `stream_stop{user}`. Neither is an error on the desktop |
| A stop before the take has started (connecting, pre-roll) | an ordinary stop, as for `live` |
| While the take is processed | the desktop keeps the connection up but no longer needs it: the phone may stop its camera, close the connection, leave the relay or send further `stream_stop`s — none of it changes the outcome. Only the desktop's own Stop (a second one, if the first ended the take) cancels: `stream_stop{user}`, the file is deleted |
| The take cannot be looped (it is mostly stalls, the remux fails, the loader refuses the result) | `stream_stop{incomplete}`; the file is deleted; what looped before is restored. Desktop text: "The recording was too incomplete to loop. Try again." |
| The connection fails during the take (`ice_failed`, `timeout`, `peer_offline`, decoder failure) | as for `live`; nothing is salvaged, the partial file is deleted |
| Size or codec changes mid-take | those frames stay out of the take until the stream is back at its original size (on a keyframe). The phone page disables Switch camera during a take |
| After the session | `loop_control` / `loop_status` as after a file: the phone can stop and start the loop while it is paired, and `start` never turns a camera on |

**The take on disk.** Under `<app data>/phone-videos/` like every phone video: a random name
(`phone-<16 hex>.part`), the directory 0700 and the file 0600, nothing from the phone in a
path. The tee file is IVF for both codecs (FourCC `VP80`, or `H264` with one Annex-B access
unit per record — the bytes the live decoder was given), which gives every frame its
timestamp: the RTP clock, or the arrival time where RTP is implausible. On a clean end the
bundled ffmpeg copies it, without re-encoding and reading nothing but that one file
(`-protocol_whitelist file -f ivf … -c copy`), into MP4 (H.264) or WebM (VP8); the result is
sniffed like a received file (`ftyp` / EBML), fsynced and renamed to `phone-<16 hex>.mp4` /
`.webm`, and loaded under the name "Phone recording.mp4" / ".webm". Partial and failed files
are deleted when the session ends, by the sweeps that follow any video load, and at exit.

**Status for the desktop UI** (`remote_stream_status`, `remote://stream-status`): `mode:
"record"` and `record: {elapsedMs, capMs: 60000, phase: "recording" | "processing" |
"looping" | "failed", error?}`. `record` is present from the request on (`recording`, 0 ms
until the take starts, then updated once a second), and stays after the session as `looping`
or `failed` (with `error`) until the next request; it is absent for live and file sessions.
`state` is `live` while recording and processing. A take that loops is announced with the
same `remote://phone-video-loaded` event as a received file.

The end-to-end authentication gap described below applies to a record session exactly as it
does to a live stream: a relay that can answer the phone can be the one whose video is
recorded.

## Known limitation / later: the offer is not authenticated end to end

**Status: not implemented. Do not rely on the relay being unable to inject video.**

WebRTC authenticates the media path with the DTLS certificate fingerprint carried in the SDP
(`a=fingerprint`). str0m verifies that the DTLS peer presents the certificate the offer
named. But the offer itself reaches the desktop through the relay, and nothing binds it to
the paired phone. The relay authenticates the two sockets (desktop token, phone ticket); it
does not — and cannot — prove to the desktop that an `offer` it forwards was written by the
phone.

What that allows: a **compromised or malicious relay** (or anyone who can act as the phone
on the relay, e.g. with a stolen phone ticket) can send `stream_request`, and after the user
clicks Accept, an `offer` with its own fingerprint and candidates, and then feed arbitrary
video into the virtual camera. It can equally replace the real phone's offer in transit.
What it does *not* allow: starting a stream without the user's Accept on the desktop,
reading the desktop's screen or files, or (for a passive relay) seeing the media, which
never touches the relay.

Mitigations in place: every stream needs an explicit Accept in the app; the dialog shows
the phone's name; the live banner and tray make a running stream visible; one click stops
it. Device names are sanitized so a request cannot disguise itself.

### Known limitation: this also covers a video sent for looping (phase 3)

**Status: not implemented (review finding M7). It applies to live streams and to video
files alike.**

A file session (`stream_request` with `mode: "file"`) is set up over the same relay
signaling as a live stream, so the same gap is there: the file's name and size in the
confirm dialog, the SDP and the DTLS fingerprint all arrive through the relay. A malicious
relay can answer the phone itself and deliver *its own* file to a user who accepted
"holiday.mp4 (12 MB)". Compared with a live stream, two things are new: the bytes are
written to disk and read by the media parsers, and the result keeps looping on the camera
after the session has ended.

What limits the damage today, without closing the gap:

- Nothing is taken without the user's Accept, and `meta` on the data channel must equal the
  file that was accepted (name, size, type).
- The content must *be* a video: the first bytes are checked (`ftyp` for mp4 / m4v / mov /
  3gp, the EBML magic for mkv / webm) before anything is kept, the stored extension comes
  from that check, and a file of another kind than announced is refused.
- ffmpeg and libavformat open a phone video with that one demuxer and the `file` protocol
  only (`-protocol_whitelist file -f mov|matroska`; `format_whitelist` for the probe), so a
  playlist or script in disguise cannot make them read other files or URLs. Files picked on
  the computer are opened as before.
- After the probe: at most 4096×4096 and 10 minutes, at most 300 MiB, stored under a random
  name in `<app data>/phone-videos/` (a real directory, mode 0700, owned by the user).
- `loop_control` can only stop the loop, or start it on a virtual camera that is already
  running; it never makes the computer raise a system prompt, and it is rate limited
  (`loop_status.error`: `busy`, `camera_off`, `rate_limited`).

The fix is the design below, extended to file sessions: an HMAC with the pairing secret `K`
over the session id, the file's metadata (name, size, type) and **both** DTLS fingerprints,
sent on the data channel and checked before `meta` is accepted.

### Proposed design

Bind the DTLS fingerprints to the pairing with a secret the relay never sees.

1. **Pairing-time secret.** Today pairing exchanges a 6-digit code *through* the relay, so
   the relay knows everything both sides know. Add a secret that travels out of band: the
   desktop generates 32 random bytes `K` and shows them to the phone in the pairing QR code
   / link **fragment** (`https://…/#k=<base64url K>` — a fragment is never sent to a
   server). Both sides store `K` with the pairing. (Typed 6-digit codes cannot carry `K`;
   for that path use a PAKE such as SPAKE2 over the code to derive `K`, or fall back to the
   verification code below.)
2. **Authenticate each offer and answer.** The phone adds to `offer`:
   `mac = base64url(HMAC-SHA256(K, "camlooper-offer-v1" ‖ 0x00 ‖ sessionId ‖ 0x00 ‖ fingerprint))`
   where `fingerprint` is the exact `a=fingerprint:sha-256 …` value of its offer (upper-case
   hex with colons). The desktop recomputes it over the fingerprint it parsed from the SDP
   and refuses the offer (`stream_stop{error}`) on mismatch, in constant time. The desktop's
   `answer` carries the same construction with the label `"camlooper-answer-v1"` over its own
   fingerprint, so the phone knows it is sending its camera to the paired computer and not
   to the relay. Covering `sessionId` prevents replaying an old offer into a new session;
   covering only the fingerprint (not the whole SDP) is enough, because everything else in
   the SDP is either authenticated by DTLS afterwards or only affects reachability.
3. **Rollout.** `hello` advertises `offerAuth: 1`. A desktop paired with `K` requires `mac`;
   pairings made before the feature have no `K` and keep today's behaviour until re-paired
   (the UI should say "re-link your phone to enable verified streaming"). Never accept a
   missing `mac` on a pairing that has `K` — that would be a downgrade.

**Alternative / fallback: a short verification code.** Without a shared secret, both
devices can display a 4-digit code derived from the two DTLS fingerprints
(`SHA-256(offerFingerprint ‖ answerFingerprint)`, truncated — a short authentication
string) once DTLS is up, and the user compares them before the desktop starts writing
frames to the camera. It needs no protocol change beyond the UI, but it costs a manual step
on every stream and users learn to click through it; the HMAC is invisible. Prefer the
HMAC, keep the code for pairings without `K`.

Related hardening to do at the same time: derive the relay `sessionId` acceptance from `K`
as well (so a relay cannot even raise the Accept dialog), and add `K`-keyed MACs to
`stream_stop` if spoofed stops become a nuisance.
